# ERP Pulse — Implementation Rules

## Purpose

These are permanent engineering rules for the ERP Pulse project.

Every implementation must follow these rules unless explicitly instructed otherwise.

---

# 1. Scope First

- Never implement work outside the approved scope.
- Never implement future sprint functionality.
- Never assume additional requirements.
- If anything is unclear, stop and ask.

---

# 2. Simplicity First

This project is an MVP.

Always prefer:

- simple
- readable
- maintainable

over

- enterprise complexity
- unnecessary abstractions
- premature optimization

Do not over-engineer.

---

# 3. Architecture Rules

Follow the project architecture exactly.

View
↓

Service
↓

Repository
↓

Database

Rules:

- Views never contain business logic.
- Views never access the database directly.
- Services contain business logic.
- Repositories perform database operations only.
- Models contain data only.
- Keep responsibilities separated.

---

# 4. NetSuite Rules

Only the integrations/netsuite module may communicate with NetSuite.

Never call NetSuite APIs from:

- Views
- Services outside integrations
- React
- Analytics
- AI

Always use:

NetSuite Client
↓

Mapper
↓

Repository

---

# 5. AI Rules

AI never calculates business metrics.

AI only explains metrics generated by the Analytics Engine.

Never send raw ERP records to the LLM.

Always send structured analytical JSON.

---

# 6. Database Rules

Current MVP database:

SQLite

Future database:

PostgreSQL

Always use Django ORM.

Never write code that depends on SQLite-specific behavior.

Changing databases should require configuration changes only.

---

# 7. Git Rules

Never generate Git commands automatically.

Never assume commits have been made.

Never assume pushes have been made.

Only suggest commit messages.

The developer performs all Git operations.

---

# 8. File Generation Rules

Never regenerate the entire project.

Only generate:

- modified files
- newly created files

Do not regenerate unchanged files.

Do not generate ZIP files unless explicitly requested.

---

# 9. Code Quality

Follow:

- PEP 8
- Small functions
- Single Responsibility Principle
- Clean Code

Avoid:

- duplicated logic
- dead code
- commented-out code
- placeholder implementations

Comments should explain WHY.

Not WHAT.

---

# 10. Security

Never:

- hardcode secrets
- commit credentials
- expose API keys

Always use environment variables.

.env is never committed.

.env.example contains placeholders only.

---

# 11. Documentation

If implementation changes project behavior:

Update documentation.

If nothing changed:

Do not modify documentation.

---

# 12. Error Handling

Never silently ignore exceptions.

Provide meaningful error messages.

Log useful information.

Do not expose internal errors to API consumers.

---

# 13. Loop Engineering

Before presenting any implementation:

Perform a complete self-review.

Check:

- Architecture
- Security
- Performance
- Scope
- Naming
- Maintainability
- Clean Code
- Documentation

If an issue is found:

Fix it before presenting the final implementation.

↓

↓

---

# 16. MVP Philosophy

ERP Pulse is a portfolio project.

The priority is:

1. Working software
2. Clean architecture
3. Readable code
4. Demonstrable features

Not:

- microservices
- Kubernetes
- event-driven architecture
- enterprise scalability
- premature optimization

Build only what is required.

Nothing more.

Nothing less.
